# Повторное ревью конкурентности и удаление лока

Проверка 2026-11-07. Промежуточный общий монитор `FilePropertySerializer`
защищал `prepare()` и запись всех подготовленных сериализаторов. Он не вызвал
заметного замедления обычного CLI, но добавил два воспроизводимых сценария
дедлока через пользовательские callbacks.

## Найденные дедлоки

1. Слушатель вызывается под монитором сериализатора, запускает сохранение
   другого файла через тот же сериализатор в другом потоке и ждёт результат.
   Работник не может войти в `prepare()`, пока слушатель держит монитор.
2. Два сериализатора сохраняют независимые файлы. Каждый listener вызывает
   `prepare()` другого сериализатора. Потоки удерживают свои мониторы и ждут
   чужие; `ThreadMXBean.findDeadlockedThreads()` обнаружил два потока в дедлоке.

Вариант до добавления общего монитора проходит оба сценария. Вариант с локом
воспроизводит оба; окончательный вариант без лока снова проходит оба.
Воспроизводитель `work/lock-review/LockCallbackProbe.java` использует публичный
API и штатный writer. Дамп потоков и результаты сравнения сохранены в
`work/lock-review/callback-probes.json` и
`work/lock-review/callback-probes-without-lock.json`.
Первоначальные JAR отличаются только двумя классами `FilePropertySerializer`;
список различий и хэши находятся в `work/lock-review/identity.json`.

## Окончательное правило

План одной сборки должен содержать уникальные выходные пути. Сначала вызывается
`prepare()` со всем списком выходов, затем каждый элемент сохраняется один раз.
Повторные выходные назначения, включая одинаковые по содержимому конфиги и
шаблоны, отклоняются до изменения файлов. Проверка учитывает существующее
разрешение symlink и нормализацию путей.

Отдельного лока и глобального реестра записываемых файлов нет. Ручные
одновременные `save()` в один файл, в том числе через разные планы или экземпляры,
считаются ошибкой вызывающего кода. Сериализатор можно переиспользовать между
последовательными независимыми сборками; получение `ConfigWriter` и сериализация
в память также не ограничены.

В `FilePropertySerializer` удалены все `@Synchronized` и блоки `synchronized`.
Проверка коллизий упрощена до множества путей: сравнивать содержимое дубликатов
больше не требуется. Набор обработанных уведомлений использует конкурентное
множество и атомарный `add`; callbacks вызываются после этой операции.
Это позволяет сохранять независимые файлы одного подготовленного плана
параллельно и применять уведомление один раз.

Остальное общее состояние штатной сборки повторно проверено: зависимости
инициализируются до работников, кэши конкурентные, рекурсивное разрешение не
удерживает блокировки внешнего кэша, YAML-деревья и parsers принадлежат операциям.
Других подтверждённых гонок или дедлоков в штатном пути при указанном контракте
не найдено. Пользовательские реализации по-прежнему считаются реализациями без
изменяемого состояния.

## Холодные запуски

Используется прежняя fixture: 50 сервисов с includes глубиной три, 100 выходных
файлов и 8850 скалярных свойств.

Во всех сравнениях **обе версии — 5.0.0**. `old` в JSON означает вариант до
общего лока, `new` — проверяемый вариант. Это не сравнение с релизом 4.9.7.
Каждый вариант запущен 11 раз для каждого сценария в новых JVM с чередованием
порядка, без прогрева и дополнительных JVM-флагов. OpenJDK 25.0.2, AC Power,
Low Power Mode выключен. Таймер полного процесса включает запуск и завершение
JVM. Кэш файлов ОС не сбрасывался. Для повторной сборки исходные 100 выходных
файлов копируются вне таймера; дополнительная seed JVM не запускается.

production JAR, но в одном заменены только два класса сериализатора на байткод
варианта до лока. Все остальные записи JAR побайтово совпадают. Подмены точки
входа, прогрева или дополнительных JVM-флагов нет. Схема и хэши сохранены в
`work/lock-review/current-packaging-identity.json`.

## Регрессионные проверки

Первый прогон без лока: **2273 теста**. После интеграции параллельных изменений
упаковки повторный `./gradlew --offline test :microconfig-cli:shadowJar`:
**2274 теста**, без падений,
ошибок и пропусков. Новые проверки покрывают запрет дубликатов для YAML и
Properties, отсутствие частичной записи при коллизии, параллельные независимые
выходы одного сериализатора, восстановление после ошибки, асинхронный вложенный
callback и взаимные обращения callbacks к разным сериализаторам. Отдельно
проверяются 32 параллельные записи разных файлов одного подготовленного плана
с одним уведомлением на файл. Тесты шаблонов сохраняют все варианты синтаксиса,
используя разные назначения для разных шаблонов.
