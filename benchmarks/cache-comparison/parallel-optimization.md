# Параллельная сборка и проверка конкурентного выполнения

Замер 2026-11-07: тот же опубликованный JAR 4.9.7, та же fixture из 50 сервисов,
OpenJDK 25.0.2, AC Power, `lowpowermode = 0`. Все изменения находятся в рабочем
дереве; состояние исходников и JAR зафиксировано в [parallel-state.json](parallel-state.json).
Предыдущий этап сохранён в [optimization.md](optimization.md).

## Холодные запуски

По семь запусков каждой версии для двух сценариев. Каждый запуск — новый
процесс `java -jar`, без прогрева и дополнительных JVM-флагов. Версии чередуются.
Кэш файлов ОС не сбрасывается. Подготовка каталогов и проверка результата
находятся вне таймера.

| Сценарий и медиана | 4.9.7 | Текущая 5.0.0 |
| --- | ---: | ---: |
| Пустой каталог: весь процесс | 418.0 мс | 418.0 мс |
| Пустой каталог: время из сообщения CLI | 369 мс | 357 мс |
| Существующий результат: весь процесс | 351.0 мс | 398.6 мс |
| Существующий результат: время из сообщения CLI | 309 мс | 349 мс |
| Пустой каталог: медиана пикового RSS | 208.7 MiB | 152.6 MiB |
| Существующий результат: медиана пикового RSS | 233.0 MiB | 193.3 MiB |

Для существующего результата в каждый выходной каталог заранее копируются
одинаковые 100 файлов из результата 4.9.7. Это проверяет сценарий повторного
вызова пользовательской команды без `-d`, включая сравнение с предыдущими
конфигами. Копирование не входит в замер и не запускает прогревочную JVM.

В последней серии свежих сборок был большой разброс: 353.3–495.0 мс у 4.9.7 и
358.6–439.5 мс у 5.0.0. В предыдущей серии из пяти запусков этого же JAR медианы
были 311.2 и 326.9 мс. Поэтому одно абсолютное число не следует считать
стабильной характеристикой машины. В серии с существующим результатом разброс
меньше: 345.9–357.8 и 388.1–402.2 мс. Здесь новая версия всё ещё медленнее на
13.6% по полному времени процесса; полного равенства в этом сценарии пока нет.

Во всех 14 парах получены 100 побайтово одинаковых файлов. Первичные данные,
точные команды, хэши JAR и ссылки на логи сохранены в
[parallel-results.json](parallel-results.json) и
[parallel-existing-results.json](parallel-existing-results.json).
Профилирование выполнялось отдельно и не включалось в эти замеры.

## Изменения

- Чтение и разрешение компонентов выполняются через `parallelStream`.
  Зависимости resolver создаются до запуска работников. Результаты и ошибки
  собираются в исходном порядке; наружу выходит исходное исключение.
- Подготовка метаданных выходных файлов и встроенного diff также параллельная.
  Разрешённые префиксы путей кешируются только внутри одного `prepare`, через
  `ConcurrentHashMap`; проверки путей при последующей очистке остаются живыми.
- Запись файлов, применение уведомлений и пользовательские слушатели сохраняют
  последовательный порядок. Новый `ConfigChangeListener.prepareAll` имеет
  стандартную реализацию через прежний `prepare`.
- При совпадении сериализованного YAML с предыдущим текстом diff не разбирает
  два одинаковых документа. Предыдущий текст берётся из переданного `FsReader`
  один раз; публичный пользовательский `ConfigIo` сохраняет прежнюю семантику.
- Для простых скаляров и построенных простых YAML mappings устранены полные
  проходы через parser/emitter. Проверяется тег нативного resolver; сложные
  значения, кавычки, anchors, теги, коллекции и блоки обрабатываются SnakeYAML.
- Для однострочных Microconfig statements не компилируется отдельный regex.
  Пустой проход обработки шаблонов не пересоздаёт свойства компонента.
- Кэш expression-only свойств атомарно вычисляет отдельное выражение через
  `computeIfAbsent`. Внешний рекурсивный кэш значений сохраняет `getOrPut`, чтобы
  рекурсивные ссылки не захватывали блокировки сегментов CHM.

Пользовательские расширения считаются реализациями без состояния и участвуют
в параллельном выполнении. Проверок их конкретного класса и последовательного
режима для них нет. Новые универсальные кэши, ThreadLocal и собственные пулы
в production-код не добавлялись.

## Конкурентное состояние

Общие кэши `FileEnvironmentRepository`, `ComponentGraphImpl`,
`FilePropertiesRepository`, `PropertiesFactoryImpl`, `StandardResolveStrategy`
и `PropertyResolutionCache` используют `ConcurrentHashMap`. Инициализация
`Microconfig.Dependencies`, `LazyInitEnvRepository` и базовых свойств `RawConfig`
использует стандартный синхронизированный Kotlin `lazy`.

`YamlSource`, `SnakeYamlTree.PropertyTree`, обход include и отдельный
`PlaceholderStatement` создаются для операций и не разделяются работниками.
Парсеры, Composer, Serializer, Emitter и их YAML nodes принадлежат одной
операции. Общий `SnakeYaml` хранит правила resolver; его чтение состояние не
изменяет. Исходники Spring 7.0.10 проверены локально: присваивания в общем
SpEL-контексте запрещены, функции регистрируются до публикации, кэши property
accessor конкурентные, внутренний parser создаётся на каждый разбор выражения.

Один `Microconfig` допускает только одну попытку сборки через `AtomicBoolean`.
Это не означает, что все публичные классы поддерживают произвольные конкурентные
вызовы. `TemplatePattern.Builder` и `TemplateDefinition` имеют изменяемые
настройки; `BinaryTemplate.contentAsBytes` и переданные коллекции также нельзя
считать глубоко неизменяемыми.

При повторном ревью подтверждён отдельный дефект API сохранения: два
одновременных `properties.save()` с одним исходным `FilePropertySerializer`
создают два подготовленных сериализатора. Их `@Synchronized` блокирует разные
объекты, поэтому запись в один файл пересекается. Воспроизводитель под
`work/concurrent-save-repro/ConcurrentSave.java` показал максимум двух
одновременных записей. Дополнительный `ConcurrentSaveStress.java` с двумя разными
неизменяемыми значениями по 512 KiB воспроизвёл смешивание их байтов штатным YAML
writer: 8 повреждённых результатов из 24 в первой серии. Повторная серия и
хэши/счётчики символов повреждённых файлов сохранены в
`work/concurrent-save-repro/stress-result.json`.
Этот сценарий не используется внутренним parallel stream
обычной одноразовой сборки. Замечание пока не исправлено.

## Проверки

`./gradlew --offline test :microconfig-cli:shadowJar` — **2264 теста**, без ошибок,
падений и пропусков. Добавлены проверки конкурентного cache miss динамического
выражения, stateless расширений, общих includes, профилей, алиасов, cross-env
ссылок, diff, порядка уведомлений и сериализации. Отдельный stress-test проверяет
16 сборок группами по четыре одновременных в разные каталоги, с общими исходниками,
циклическими defaults, алиасами одного оригинального компонента и шаблонами.
Ещё два теста выполняют по 256 параллельных операций с общим YAML writer и SpEL
resolver, включая anchors/merge и неуспешные присваивания в SpEL.

Для повторного замера:

```sh
./gradlew --offline :microconfig-cli:shadowJar
python3 benchmarks/cache-comparison/run.py \
  --old-jar /path/to/microconfig-cli-4.9.7.jar \
  --new-jar microconfig-cli/build/libs/microconfig-cli-5.0.0.jar \
  --java /path/to/java \
  --runs 7 \
  --results benchmarks/cache-comparison/work/repeat-parallel.json
```

Для повторной сборки добавить `--existing-output /path/to/previous/output`.
